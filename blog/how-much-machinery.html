How Much Machinery Does Your GenAI Feature Actually Need?

September 2026

Most of what gets written about building with LLMs starts with the complicated version: an agent, a tool registry, a planner, a retrieval layer, maybe a second model to critique the first. It is genuinely fun to build, and for plenty of problems it is the right answer. But it has quietly set a default, and the default is wrong often enough to be worth questioning. The honest starting point for most real work is one prompt, run once, over a handful of inputs you have read with your own eyes.

Anthropic puts this plainly in Building Effective AI Agents: find the simplest solution possible, and only increase complexity when needed. That might mean, they add, not building an agentic system at all. OpenAI's practical guide to building agents arrives at the same place from the other direction: maximize what a single agent can do before you split it into several. Both of those come from companies that would be delighted to sell you the complicated version. Worth noticing.

So the interesting question isn't "simple or complex." It is: how do you know when you have earned the next level of complexity? This post is a practical answer, aimed at engineers building something real with LLMs without a background in the space, which, thanks to how good the tooling has got, is now a lot of the people shipping interesting things. I'm not the authority here. This is the order I work in, and what each step has cost me.

Start simple, then look at what broke

Before the first prompt, write down what "correct" means for twenty specific inputs. Not a rubric, not a vibe. Twenty actual cases with the behaviour you'd accept for each. This takes an afternoon and it is the single highest-leverage thing in the whole project, because everything downstream is a comparison against it. If you can't say what correct looks like on twenty cases, no architecture is going to rescue you.

Then build the simplest version: one prompt, one call, the cheapest model that could plausibly do it. Run all twenty. Read every output, all the way through. This baseline is not a strawman you set up to knock down; it's the number every later decision has to beat, and it is very often better than people expect.

Then do error analysis, which is a grand name for a simple thing: for each bad output, write one line about what went wrong, then group the lines and count the groups. Hamel Husain's version of this advice is blunter and better: look at your data, read a hundred traces, label the errors, count the categories. His point that stuck with me is that the reflex to reach for an LLM judge is usually premature. The better move is often to remove or simplify something before you automate the judging of it.

At the end of an afternoon you will have something far more valuable than an architecture diagram: a ranked list of how your system actually fails. That list is what tells you what to build next, and it is the thing almost everyone skips.

What to add, and in what order

Here is roughly how I think about the levels of complexity. Each one buys you something specific and charges you for it.

LevelWhat you addThe failure it fixesWhat it costs
0One prompt, one callNone. This is your baselineAlmost nothing
1Examples in the prompt, a fixed output schemaFormat drift, inconsistent shapeA few tokens
2Better context: retrieval, or deterministic pre-computationThe model doesn't know somethingAn index or lookup to maintain
3Split into stages (a workflow)Two failure modes fighting inside one promptN× latency and cost, but N inspectable intermediates
4Let the model choose the path (tools, agentic loop)The path genuinely varies per inputNon-determinism, unbounded cost, much harder evals
5More thinking (reasoning model, higher effort)Multi-step reasoning where one wrong early step ruins the answerRoughly 5–50× per token, and seconds of latency

The rule I try to hold myself to: move up a level when error analysis says one class of failure dominates, and that level is the cheapest thing that addresses it. Not before, and not two levels at once, because then you can't attribute the improvement to either.

Three of these are worth a note, because they're where people slip.

Level 2 is underrated. A lot of what people reach for a model to do is really a missing piece of context, or a job a hundred lines of ordinary code can do perfectly. If the task is a lookup, a rule, a regex, or a schema validation, write the code: it's free, it's identical on every run, and when it breaks you can point at the line that did it.

The best reason to split a prompt is not capability. People usually justify breaking one call into three by saying the model couldn't do it all at once. Often it could. The better reason is that stages fail differently, and when a rewriting step that fails by being wrong shares a prompt with a formatting step that fails by being malformed, the two trade off invisibly. Split apart, with each intermediate output saved, a bad result tells you which stage broke it. The real reason to add a stage is observability, not capability.

Level 5 is not a free upgrade. Reasoning models earn their cost when a wrong intermediate step ruins the answer: planning, multi-step analysis, hard code. For rewriting, classification, summarizing and anything high-volume, a standard model usually wins on speed and price without losing accuracy. The returns are front-loaded, so the jump from no reasoning to some is steep while high to maximum is nearly flat.

Where solutions actually land

Worth knowing what the plausible end states look like, because the discourse implies there's only one.

  • A single well-built call. One prompt, a few examples, a fixed schema, a cheap fast model. Classification, extraction, rewriting, tagging, routing: a good share of useful features are this and nothing more.
  • A call wrapped in ordinary code. Deterministic work before it to assemble the right context, deterministic work after it to validate and to enforce what the model shouldn't be trusted with. This is where I land most often, and the shape hardest to find written up, because it isn't exciting.
  • A short fixed chain. Two to four calls in a known order, each output inspectable. Predictable cost, predictable latency, and you always know where a failure happened.
  • An actual agent loop. Right when the path genuinely varies per input and can't be known in advance. OpenAI's guide gives two honest triggers: your prompt has become spaghetti conditional logic, or it holds objectives that actively conflict. "It would be cool" is not one of them.

And a fifth nobody advertises: going back down. Some of the best changes I've made have been deleting a stage that worked. A component can function correctly and still not earn its keep, because it costs latency and money, it can drift, and your evals have to cover it. If you can remove it and the numbers hold, remove it.

The cost of complexity you didn't need

Every stage and rule you add is a parameter fit to the cases you happen to have seen. Enough of them and you've built something tuned to your twenty examples and nothing else, which stays invisible until you ship.

The defence is boring and it works: iterate against a dev set, seal off a slice (20% is a reasonable default), and look at it only when you ship. If dev says 90 and the holdout says 70, your prompt memorized your dev cases instead of solving the task. Run forty experiments against one eval set and you'll find an improvement that isn't there, because the number surviving forty comparisons is the maximum of forty noisy measurements, and that flatters you.

Worth knowing too: when a check fails to catch something, the bug is usually in the spec rather than the pipeline. If two careful readers disagree about whether an output passed, fix the task definition before you touch the prompt, or you will tune a good system against a broken test.

If you're starting this week

  1. Write down twenty real inputs and what a correct output looks like for each, before you write a prompt.
  2. Build the simplest version: one prompt, one call, cheapest capable model. Run all twenty and read every output.
  3. Label what went wrong and count the categories. The biggest one is your next piece of work.
  4. Fix it with the cheapest thing that could: deterministic code before a model call, a prompt change before a new stage, a new stage before an agent loop.
  5. Re-run. Did that category shrink without others growing? If not, take the change back out.
  6. Seed a few defects into known-good outputs and confirm your metric sees them. If it can't, fix the metric first.
  7. Before you ship, run the holdout you haven't looked at.

None of this is an argument against agents. They're the right call when the path genuinely varies and the value of handling it absorbs the cost of non-determinism. It's an argument for being able to say why you built one, and for knowing what the simpler version scored. The tooling has got good enough that building the complicated version is no longer the hard bit. Knowing whether you needed it is.

I'd genuinely like to hear where other people stopped adding complexity, what made them add the next piece, and what they later took back out. That last one is the answer I learn the most from and see written down the least.
