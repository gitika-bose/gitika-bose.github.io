How Much Machinery Does Your GenAI Feature Actually Need?

September 2026

Most of what gets written about building with LLMs starts with the complicated version: an agent, a tool registry, a planner, a retrieval layer, maybe a second model to critique the first. It is genuinely fun to build, and for plenty of problems it is the right answer. But it has quietly set a default, and the default is wrong often enough to be worth questioning. The honest starting point for most real work is one prompt, run once, over a handful of inputs you have read with your own eyes.

Anthropic puts this plainly in Building Effective AI Agents: find the simplest solution possible, and only increase complexity when needed. That might mean, they add, not building an agentic system at all. OpenAI's practical guide to building agents arrives at the same place from the other direction: maximize what a single agent can do before you split it into several. Both of those come from companies that would be delighted to sell you the complicated version. Worth noticing.

So the interesting question isn't "simple or complex." It is: how do you know when you have earned the next level of complexity? This post is a practical answer, aimed at engineers building something real with LLMs without a background in the space, which, thanks to how good the tooling has got, is now a lot of the people shipping interesting things. I'm not the authority here. This is the order I work in, and what each step has cost me.

Start at the floor, and make the floor real

Before the first prompt, write down what "correct" means for twenty specific inputs. Not a rubric, not a vibe. Twenty actual cases with the behaviour you'd accept for each. This takes an afternoon and it is the single highest-leverage thing in the whole project, because everything downstream is a comparison against it. If you can't say what correct looks like on twenty cases, no architecture is going to rescue you.

Then build the simplest version: one prompt, one call, the cheapest model that could plausibly do it. Run all twenty. Read every output, all the way through. This baseline is not a strawman you set up to knock down; it's the number every later decision has to beat, and it is very often better than people expect.

Then do error analysis, which is a grand name for a simple thing: for each bad output, write one line about what went wrong, then group the lines and count the groups. Hamel Husain's version of this advice is blunter and better: look at your data, read a hundred traces, label the errors, count the categories. His point that stuck with me is that the reflex to reach for an LLM judge is usually premature. The better move is often to remove or simplify something before you automate the judging of it.

At the end of an afternoon you will have something far more valuable than an architecture diagram: a ranked list of how your system actually fails. That list is what tells you what to build next, and it is the thing almost everyone skips.

What to add, and in what order

Here is roughly how I think about the levels of complexity. Each one buys you something specific and charges you for it.

LevelWhat you addThe failure it fixesWhat it costs
0One prompt, one callNone. This is your baselineAlmost nothing
1Examples in the prompt, a fixed output schemaFormat drift, inconsistent shapeA few tokens
2Better context: retrieval, or deterministic pre-computationThe model doesn't know somethingAn index or lookup to maintain
3Split into stages (a workflow)Two failure modes fighting inside one promptN× latency and cost, but N inspectable intermediates
4Let the model choose the path (tools, agentic loop)The path genuinely varies per inputNon-determinism, unbounded cost, much harder evals
5More thinking (reasoning model, higher effort)Multi-step reasoning where one wrong early step ruins the answerRoughly 5–50× per token, and seconds of latency

The rule I try to hold myself to: move up a level when error analysis says one class of failure dominates, and that level is the cheapest thing that addresses it. Not before, and not two levels at once, because then you can't attribute the improvement to either.

A few of these deserve a note, because they're where people slip.

Level 2 is underrated and level 4 is overrated. An enormous amount of what people reach for an agent to do is really a missing piece of context, or a job a hundred lines of ordinary code can do perfectly. If the task is a lookup, a rule, a table join, a regex, or a schema validation, write the code. It's free, it's instant, it's identical on every run, and when it goes wrong you can point at the line that did it. Every job a deterministic component can carry is one less thing your evals have to be able to see.

The best reason to split a prompt is not capability. When people justify breaking one call into three, they usually say the model couldn't do it all at once. Often it could. The better reason is that different stages fail in different ways. A rewriting step fails by being wrong; a formatting step fails by being malformed. When those share a prompt, they trade off against each other invisibly. Split apart, with each stage's intermediate output persisted, a bad result tells you which stage broke it. The underrated reason to add a stage is observability, not capability.

Level 5 is not a free upgrade. Reasoning models are for problems where a wrong intermediate step ruins the answer: multi-step analysis, planning, hard code. For lookup, rewriting, classification, summarization and anything high-volume, a standard model usually wins on speed and price without losing accuracy. Thinking tokens run roughly 5–50× standard cost with real added latency, and the returns are front-loaded. The jump from no reasoning to some is steep; the climb from high to maximum effort is nearly flat. Treating a reasoning model as a strict upgrade is the expensive mistake.

Where solutions actually land

It's worth knowing what the plausible end states look like, because the discourse implies there's only one.

A single well-built call. One prompt with a few good examples and a fixed output schema, on a cheap fast model. Classification, extraction, rewriting, summarizing, tagging, routing: a good share of useful GenAI features are this and nothing more. If this is where you land, you have not failed to build something impressive. You have avoided paying for machinery you didn't need.

A call wrapped in ordinary code. Deterministic work before the call to assemble exactly the right context, and deterministic work after it to validate, normalize, or enforce rules the model shouldn't be trusted with. This is the shape I end up at most often, and the one that's hardest to find written up, because it isn't exciting. It is, however, usually the one that survives contact with production.

A short fixed chain. Two to four calls in a known order, each doing one job, each output inspectable. Predictable cost, predictable latency, and you always know where a failure happened. Anthropic's framing is useful here: workflows give you predictability and consistency for well-defined tasks, agents give you flexibility and model-driven decisions at scale. If your task is well-defined, take the predictability.

An actual agent loop. The right call when the path genuinely varies per input and can't be known in advance, and when the value of handling that variety absorbs the cost of non-determinism. OpenAI's guide gives two honest triggers for escalating: your prompt has turned into spaghetti conditional logic (if X then Y, unless Z, then A…), or you have objectives inside one prompt that actively conflict. Those are good signals. "It would be cool" is not.

And there's a fifth outcome nobody advertises: going back down. Some of the best changes I've made to LLM systems have been deleting a stage that worked. A component can function correctly and still not earn its keep. It costs latency, it costs money, it's one more thing that can drift, and it's one more thing your evals have to cover. If you can remove it and the numbers hold, remove it. Being willing to delete the thing you just built is most of the skill.

You can't tell what helped without a ruler

Everything above depends on being able to tell whether a change helped. This is where new builders get hurt most, and it's rarely because they skipped evaluation entirely. Usually they have a metric. The problem is that the metric can't see the thing they changed.

Here's a cheap technique that's worth running before you trust any metric: seed defects. Take a handful of outputs your system got right, and plant exactly one deliberate error in a copy of each, the kind of error that would actually hurt a user. Then check whether your metric notices.

I did this on a text-simplification system that scored its own output for readability, and the result was uncomfortable. Across two dozen deliberately broken variants (altered numbers, invented facts, a dropped instruction, a softened warning) the readability score never moved more than five points in either direction. One whole class of defect raised it, because invented content tends to be short and plain and easy to read. The score wasn't broken. It was measuring readability faithfully, and being wrong is not the same as being hard to read.

What caught them was dull, deterministic checking: does every number in the output trace back to the source, does the thing that was supposed to survive actually appear, is the text that should never appear absent. No model involved. That found about seventy percent of the planted defects. It also found, on the untouched outputs, one real defect nobody had planted.

Three lessons came out of it.

The ruler has to be able to see the change. If you add a stage to fix fabricated content and your only metric is readability, you have no idea whether it worked. You will keep the stage anyway, because you built it and removing it feels irresponsible. That is exactly how systems accumulate machinery nobody can justify.

Grade in tiers, cheapest first. Deterministic checks wherever the contract is genuinely checkable, an LLM judge only for what code cannot check, humans to calibrate the judge. The same discipline applies to your evals as to your pipeline: an LLM judge is a level-4 decision for your eval layer, and it has to be earned the same way. It also has to be validated. A judge is only trustworthy once it agrees with human labels often enough, and it needs re-checking whenever its prompt or model changes.

For anything a person will act on, the metric is pass^k, not pass@k. Run every case several times and count it as passing only if every run passes. LLMs are non-deterministic; a feature that's right four times out of five is not right, and a single-run eval will happily hide that from you.

The cost of complexity you didn't need

Every stage, rule and heuristic you add is a parameter you have fit to the cases you happen to have seen. Enough of them and you have built something exquisitely tuned to your twenty examples and nothing else. This is the real cost of overbuilding, and it's invisible until you ship.

The defence is boring and it works: keep a holdout. Iterate freely against a dev set, seal off a slice (20% is a reasonable default) and look at it only when you ship. If the dev score is 90 and the holdout is 70, your prompt has memorized your dev cases rather than solved the task. Put another way: run forty experiments against one eval set and you will find an improvement that isn't there, because the number that survives forty comparisons is the maximum of forty noisy measurements, and the maximum of noisy measurements flatters you.

There's a subtler version of this that surprised me. When I've gone back to examine why a check failed to catch something, the bug has usually been in the specification, not the pipeline: a threshold set too leniently to ever trigger, or a rule matching against the whole output so that a deletion in one section hid behind the same words appearing in another. If two careful readers disagree about whether an output passed, that's a bug in your task definition, not in the model. Fix the spec before you touch the prompt, otherwise you'll tune a perfectly good system against a broken ruler.

If you're starting this week

  1. Write down twenty real inputs and what a correct output looks like for each. Do this before you write a prompt.
  2. Build the simplest version: one prompt, one call, cheapest capable model. Run all twenty. Read every output.
  3. Label what went wrong and count the categories. The biggest category is your next piece of work.
  4. Fix that one category with the cheapest thing that could fix it. Deterministic code before a model call; a prompt change before a new stage; a new stage before an agent loop.
  5. Re-run. Did that category shrink without others growing? If not, take the change back out.
  6. Seed a few defects into known-good outputs and confirm your metric can actually see them. If it can't, fix the metric before you build anything else.
  7. Before you ship, run the holdout you haven't looked at.

None of this is an argument against agents. Agentic systems are the right call when the path genuinely varies per input and the value of getting it right absorbs the cost of non-determinism. It is an argument for being able to say why you built one, and for knowing what the simpler version scored.

If you're new to this space, that last part is the whole edge. The tooling has got good enough that building the complicated version is no longer the hard bit. Knowing whether you needed it is.

What I'd like to know

I'd genuinely like to hear where other people stopped adding complexity, what made them add the next piece, and what they later took back out. That last one is the answer I learn the most from and see written down the least.
